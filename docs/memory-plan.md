# 메모리 계획

전체 플랫폼(쿠폰·인증·Gateway·알림·파일 서버 + 공용 미들웨어 + 운영 도구)이 다 올라갔을 때를 기준으로 세운 예산이다.
새 구성요소를 넣을 때는 아래 예산표를 먼저 고치고, 합계가 VM 메모리를 넘지 않는지 확인한다.

## 맥 사양 (2026-10-20 확인)

- Apple M2 Pro, CPU 10코어, 메모리 16GB, 디스크 남은 공간 89GB
- Docker Desktop: 처음 7.75GB → 3GB로 줄임

## 맥 메모리 16GB 나누기 (지금)

- macOS + 브라우저 + IDE: 약 5GB
- VM 3대: 8GB (cp1 2GB, worker1 3GB, worker2 3GB)
- Docker Desktop: 3GB. 여유가 거의 없으므로 클러스터 작업을 할 때는 Docker Desktop을 꺼두는 것이 가장 좋다.

Multipass(QEMU)는 VM에 준 메모리를 처음부터 다 잡지 않고 VM 안에서 쓰는 만큼 가져간다.
하지만 서비스가 다 올라가면 거의 다 쓰게 되므로 예산은 최대치로 잡는다.

## 실측 (3단계 MySQL 배포 후, 2026-10-20)

VM 안 `free -m` 기준. VM의 실제 총량은 커널 몫을 빼고 cp1 1955MB, worker 2956MB다.

- cp1: used 870~1216MB, available 740~1085MB (k3s-server가 약 1GB, 시간에 따라 흔들림)
- worker1: k3s agent + OS 약 370MB. MySQL을 올리고 100만 줄을 넣은 직후 used 751MB
- worker2: k3s agent + OS + Traefik 약 400MB
- MySQL 파드 (cgroup): 재시작 직후 151MiB → 100만 줄 넣은 직후 620MiB (실제 사용 anon 403MiB + 파일 캐시 209MiB)
  - 파일 캐시는 메모리가 부족하면 커널이 돌려받는다. limit 768Mi는 이 최대치보다 150MB 정도 여유가 있다

## 예산표 (limit 기준 = 최악의 경우)

"측정"은 실제로 잰 값, "추정"은 공식 문서·흔한 설정 기준의 예상치다. 단위 MB.

```
노드 (실제 총량)        구성요소                     예산   근거
───────────────────────────────────────────────────────────────────────
cp1 (1955)              k3s server + 기본 구성요소   1216   측정 최대치
                        (taint: 앱 파드 금지)         ────
                                                     남음 약 740
───────────────────────────────────────────────────────────────────────
worker1 (2956) 데이터   OS + k3s agent                370   측정
                        MySQL                         768   limit (측정 최대 620)
                        Redis 7                       128   추정 (실사용 30~60)
                        Kafka 1대 (KRaft, 힙 512M)    768   추정
                                                     ────
                                                     2034   남음 922
───────────────────────────────────────────────────────────────────────
worker2 (2956) 앱       OS + k3s agent + Traefik      400   측정
                        쿠폰 서버 × 2                1024   limit 512 × 2 (추정)
                        Gateway·인증·알림·파일 × 4  1792   limit 448 × 4 (추정)
                                                     ────
                                                     3216   부족 260
───────────────────────────────────────────────────────────────────────
어디든 (워커)           ArgoCD (최소 구성)            600   추정: controller 300, repo-server 150, server 100, redis 50
                        모니터링 (Prometheus 계열)    900   추정: Prometheus 500, Grafana 150, operator·exporter 250
───────────────────────────────────────────────────────────────────────
워커 합계               필요 6750 / 용량 5912 → 약 840 부족 (여유 0%)
```

## 판단

- 질문에 나온 것만(Redis, Kafka, 쿠폰 서버 2개, ArgoCD, 모니터링) 올리면: 필요 4958 / 용량 5912 → **들어간다** (여유 950MB, 16%)
- 전체 계획(나머지 서비스 4개 포함)까지 올리면: **약 840MB가 모자라고 여유도 없다** → 지금 VM 크기로는 안 된다
- 여유는 용량의 15% 정도는 남겨야 한다. limit을 꽉 채우면 노드 메모리 압박으로 파드가 쫓겨난다(eviction)

### 해결 방법

1. **워커를 3GB → 4GB로 늘린다** (추천)
   - VM 합계 8GB → 10GB. 맥: macOS 5 + VM 10 = 15GB → Docker Desktop은 클러스터를 쓸 때 꺼야 한다
   - 컨테이너 이미지 빌드는 GitHub Actions(public 저장소 무료)에서 하거나, 빌드할 때만 Docker Desktop을 켠다
   - 워커 용량 7912 → 필요 6750, 여유 1160MB (15%)
   - 방법: `multipass stop worker1 && multipass set local.worker1.memory=4G && multipass start worker1` (worker2도), `multipass/vms.conf`도 고친다
2. **3GB를 유지하고 가벼운 도구로 바꾼다**
   - 모니터링: Prometheus 대신 VictoriaMetrics 단일 실행 + Grafana (약 -500)
   - ArgoCD: core 설치(웹 UI 없이 CLI만) (약 -200)
   - Kafka 힙 384M (약 -200), Spring 앱 limit 384Mi (약 -450, OOM 위험)
   - 필요 약 5400 / 용량 5912 → 여유 8%. 빠듯하고 Spring 앱이 OOM으로 죽을 위험이 있다
3. **3GB를 유지하고 한 번에 다 띄우지 않는다**: 실습하는 서비스만 replicas 1, 나머지는 0

## MySQL을 하나만 두는 이유

- MySQL 서버 하나는 아무것도 안 해도 150~400MB를 쓴다 (실측: 재시작 직후 151MiB, 데이터를 쓰면 620MiB까지).
  서비스마다 따로 두면 4개 × 768MB limit = 3GB가 들고, 하나로 합치면 768MB면 된다.
- 대신 서비스끼리 데이터를 섞지 않도록 DB를 나누고, 계정마다 자기 DB에만 권한을 준다 (docs/mysql.md).
  → 실무의 "서비스별 DB 분리" 원칙을 지키면서 물리 서버만 공유하는 방식이다.
- 단점: MySQL이 죽으면 모든 서비스가 같이 멈춘다. 서비스 하나의 무거운 쿼리가 다른 서비스를 느리게 할 수 있다 (계정별 연결 수 제한으로 일부 막음).

## VM을 3대로 하는 이유 (2대와 비교)

- 2대(컨트롤 플레인 1 + 워커 1)면 VM 하나만큼 운영체제·k3s 오버헤드(약 300MB)를 아낄 수 있다.
- 하지만 워커가 1대면 "파드를 여러 노드에 나눠 배치", "노드 하나를 비우고(drain) 다른 노드로 옮기기", "노드 장애" 같은 쿠버네티스의 핵심 실습을 할 수 없다.

## 디스크

- cp1 15GB, worker1·worker2 각 20GB = 최대 55GB. 실제로는 쓴 만큼만 늘어난다 (thin provisioning).
- worker1의 MySQL 데이터(`/srv/data/mysql`)는 빈 상태 약 280MB, 100만 줄(80MB 테이블)을 넣었을 때 363MB. 백업은 같은 100만 줄이 gzip으로 7.5MB.
- local PV의 용량(5Gi)은 강제되지 않는다. worker1에서 `df -h /`로 가끔 확인한다.
